# Задания бэкендера 2 простыми словами

Ты отвечаешь за сервер приложения: запросы браузера, сохранение пользовательских данных, проверку правил и журнал результатов. Физику датчика и лампы предоставляет бэкендер 1.

Сначала прочитай [общее объяснение бэкенда](%D0%91%D1%8D%D0%BA%D0%B5%D0%BD%D0%B4%20%D0%BF%D1%80%D0%BE%D1%81%D1%82%D1%8B%D0%BC%D0%B8%20%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D0%BC%D0%B8.md). Оно нужно обоим: вы пишете разные части одной программы.

**Первый результат:** через HTTP можно сохранить правило «Если leak_1 сообщает leak=1, включить lamp у light_1», а затем проверить его на настоящих объектах эмуляторов.

## Твоя часть общей архитектуры

```text
Браузер
   |
Твой app.py: принять запрос и вернуть ответ
   |
   +--> schemas.py: проверить данные пользователя
   +--> storage.py: сохранить и прочитать данные
   +--> scenario_engine.py: проверить условие и выполнить действия
                      |
                      v
           runtime бэкендера 1: прочитать или изменить устройство
```

Тебе не нужно самостоятельно считать температуру и заряд батареи. Вызываешь функции `runtime`. Для внешней публикации не создаёшь второй клиент Ujin: отдаёшь изменения адаптеру бэкендера 1.

**Маршрут API** — адрес, по которому браузер просит сделать определённую работу. **Обработчик маршрута** — Python-функция, которая выполняется, когда приходит запрос по этому адресу.

## Шаг 1 Поднять маленький сервер

**Зачем:** получить первый работающий адрес, прежде чем добавлять базу, правила и устройства.

Договорись, где корень нового приложения. Создай папку `backend`, пустой файл `backend/__init__.py` и файл `backend/app.py`:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/api/health")
def health():
    return {"ok": True}
```

`FastAPI()` создаёт приложение. Строка `@app.get(...)` связывает GET-запрос по адресу с функцией ниже. Возвращённый словарь превратится в JSON для браузера. [Официальный первый пример FastAPI](https://fastapi.tiangolo.com/tutorial/first-steps/) объясняет этот механизм.

Из корня нового приложения:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install "fastapi[standard]"
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Эти команды для macOS/Linux. Первая создаёт **виртуальное окружение** — отдельное место для библиотек проекта. Вторая включает его. Третья устанавливает библиотеку. Четвёртая запускает сервер. `backend.app:app` означает «объект app из файла backend/app.py».

Пока сервер работает, открой `http://127.0.0.1:8000/api/health`. Для первого совместного запуска используем один процесс, без автоматической перезагрузки. Позже важно не создать два независимых набора эмуляторов.

**Проверка готовности:** виден ответ `{"ok":true}`. Фронтендер знает адрес. `/docs` позволяет просматривать и пробовать описанные маршруты; это удобный инструмент разработки FastAPI.

## Шаг 2 Подключить устройства бэкендера 1

**Зачем:** браузер должен читать и изменять те же устройства, с которыми работают правила.

Получи у бэкендера 1 `DeviceRuntime`. Создай **один** экземпляр при запуске сервера. Храни ссылку на него в состоянии приложения и передавай в обработчики. Не делай `DeviceRuntime()` заново при каждом запросе.

Сначала добавить:

| Наш адрес | Что сделать внутри |
| --- | --- |
| `GET /api/devices` | Вызвать `runtime.list_devices()` |
| `GET /api/devices/{id}` | Собрать описание и состояние выбранного устройства |
| `POST /api/devices/{id}/commands` | Проверить тело и вызвать `runtime.apply_command()` |
| `POST /api/devices/{id}/simulate` | Проверить тестовый вход и вызвать `runtime.simulate()` |

`{id}` означает переменную часть пути. В `/api/devices/light_1` значение id — `light_1`.

Тело команды лампе:

```json
{"signal":"lamp","value":1}
```

Тело симуляции протечки:

```json
{"input":"wet","value":true}
```

Симуляция воды сначала устанавливает внешнее условие, а сигнал `leak` изменится на ближайшем тике. Не сообщай, что весь сценарий уже завершён в момент принятия такого запроса.

Договорись с фронтендером о точном ответе карточки: id, название, семейство, список описаний сигналов, значения и статус интеграции. Длинные серийные номера Ujin возвращать строками.

**Проверка готовности:** через наш API можно включить лампу, прочитать её и увидеть 1. Для этого фронтенд пока не обязателен: достаточно `/docs` или HTTP-клиента.

## Шаг 3 Представить правило как данные

**Зачем:** пользователь должен сам задавать разные правила. Поэтому правило хранится в JSON, а не в отдельном Python-файле на каждый случай.

Начальный формат:

```json
{
  "id": "scenario_1",
  "title": "Свет при протечке",
  "enabled": true,
  "condition": {
    "device_id": "leak_1",
    "signal": "leak",
    "operator": "==",
    "value": 1
  },
  "actions": [
    {"device_id": "light_1", "signal": "lamp", "value": 1}
  ]
}
```

`condition` — условие «если». `actions` — список действий «то». `enabled` — включено ли правило. Список нужен, чтобы позже одно правило могло выполнить несколько действий. Для первого прохода хватит одного.

Id нового правила выдаёт сервер. Название задаёт пользователь. Поддержи сначала `==` — равно, затем `>` — больше и `<` — меньше. Для двоичных и перечисляемых значений оставь сравнение на равенство.

Добавить создание, список, изменение, включение/выключение и удаление правил. Пути согласовать с фронтендером по общему плану.

**Проверка готовности:** можно отправить правило на сервер и получить его обратно без потери значений. Пока без автоматического выполнения.

## Шаг 4 Проверять данные до сохранения

**Зачем:** браузер может прислать ошибочное значение. Сервер не должен принимать невыполнимое правило.

Сделай модели входных данных в `schemas.py`. **Схема** описывает, какие поля обязательны и какие типы они принимают. В FastAPI для этого обычно используют модели Pydantic; это библиотека проверки данных.

Затем дополнительно проверить смысл:

1. Устройства условия и действий существуют.
2. Сигнал условия можно читать: доступ `r` или `rw`.
3. В сигнал действия можно писать: доступ `rw` или `w`.
4. Оператор подходит типу.
5. Значение имеет правильный тип и входит в разрешённый диапазон.
6. Название не пустое, действий допустимое количество.

Число `1` и строка `"1"` различаются. Для переключателей нашего API договорились о числах 0/1. Не допускай случайного сравнения строки с числом. Если приведение типов разрешено, оно должно быть явным и одинаковым для всех запросов.

Пример отказа: «Сигнал leak доступен только для чтения». Вернуть HTTP 422 и понятное тело ошибки. **HTTP-статус** — короткий числовой результат запроса: например, 200 — успех, 404 — объект не найден, 422 — данные не подходят.

Не использовать `eval` для выполнения текста условия. Эта функция исполняет Python-код; нам нужны обычные сравнения проверенных значений.

**Проверка готовности:** правило с записью в `leak` и правило с недопустимой яркостью не сохраняются, причина понятна фронтендеру.

## Шаг 5 Сохранять данные в SQLite

**Зачем:** если всё держать только в переменных Python, после перезапуска исчезнут созданные правила и устройства.

Сделай `storage.py`. Для первой версии достаточно трёх таблиц. **Таблица** — набор записей одинакового назначения, как отдельный лист с данными.

| Таблица | Что хранить |
| --- | --- |
| `device_definitions` | Id и JSON-описание созданного устройства |
| `scenarios` | Id, название, включённость и JSON условия/действий |
| `execution_logs` | Id, время, id сценария, результат и подробности выполнения |

Можно хранить сложную часть записи JSON-текстом. Это позволяет не строить много связанных таблиц для первого прототипа. Напиши функции `save_scenario`, `list_scenarios`, `save_device`, `list_devices`, `add_execution`, `list_executions`.

Используй параметры SQL-запросов, например `WHERE id = ?`, вместо склеивания текста с пользовательским вводом. **SQL** — язык запросов к базе данных. Подстановка через параметры отделяет запрос от значения.

Сохраняй изменение и подтверждай запись в базу до ответа об успехе. Если запись не удалась, не показывай, что правило сохранено. Обновление активного списка правил и базы согласуй под общей блокировкой, чтобы движок не читал половину изменения.

Для простого варианта каждая операция `storage.py` открывает своё соединение с SQLite, выполняет короткую работу и закрывает соединение в том же потоке. Не передавай одно глобальное соединение между HTTP-обработчиками и фоновым циклом: по умолчанию sqlite3 ограничивает использование соединения создавшим его потоком. [Документация sqlite3](https://docs.python.org/3.13/library/sqlite3.html).

**Проверка готовности:** после остановки и нового запуска сервера список содержит ранее созданное правило. Ошибка записи не превращается в успешный ответ.

## Шаг 6 Написать проверку условия

**Зачем:** система должна сама решать, пора ли выполнить действие.

В `scenario_engine.py` напиши функцию проверки одного условия:

1. Взять `device_id` и `signal` из сохранённого правила.
2. Получить значение через `runtime.get_state()`.
3. В зависимости от `operator` выполнить сравнение.
4. Вернуть `True` или `False` — да или нет.

Пример отдельной функции сравнения числовых значений:

```python
def compare(actual, operator, expected):
    if operator == "==":
        return actual == expected
    if operator == ">":
        return actual > expected
    if operator == "<":
        return actual < expected
    raise ValueError("Неизвестный оператор")
```

До этой функции данные уже должны пройти проверку типа. Она показывает идею сравнения, но не заменяет проверки устройства, сигнала и типов.

Если условие стало истинным, пройти по `actions` и для каждого действия вызвать `runtime.apply_command(device_id, signal, value)`.

Не писать в движке отдельное условие `if device_id == "leak_1"`. Движок должен понимать данные любого допустимого правила. Тогда пользователь сможет выбрать новый датчик без изменения программы.

**Проверка готовности:** один и тот же код исполняет правило протечки и другое правило по числовому сигналу.

## Шаг 7 Не выполнять одно правило каждую секунду

**Зачем:** постоянная протечка — одно событие начала тревоги, а не повод каждую секунду повторять действие.

Храни для каждого правила предыдущий результат условия. **Переход false → true** означает: раньше условие не выполнялось, а теперь выполняется.

| Было | Стало | Что делаем |
| --- | --- | --- |
| false | false | Ничего |
| false | true | Выполняем действия один раз |
| true | true | Ничего |
| true | false | Запоминаем, что условие снова не выполнено |

При создании, включении или изменении правила сначала вычисли текущее условие и запомни его. В нашем MVP действия ждут следующего перехода. Если включить правило при уже мокром датчике, немедленного запуска не будет. Это поведение нужно объяснить фронтендеру и проверить.

Для первого объединения можно после каждого тика проверять все включённые правила: их мало. Обязательно обновлять прошлый результат при переходе обратно в false. Позднее можно проверять только правила, связанные с изменившимся сигналом.

Если действие одного правила запускает другое, возникает цепочка. Не вызывай движок рекурсивно без ограничения. Используй список ожидающих изменений. Дай цепочке общий id, например `causation_id`, и запоминай, какие правила уже выполнялись в этой цепочке. Одно правило — не больше одного выполнения на цепочку, общий предел — например 20 обработанных событий.

`causation_id` означает «идентификатор первоначальной причины». Он нужен, чтобы объяснить связи в журнале и остановить петлю «А включает Б, Б включает А».

**Проверка готовности:** протечка в течение десяти тиков даёт одно выполнение; после сухо → мокро появляется второе; выключенное правило не срабатывает.

## Шаг 8 Записывать понятный журнал

**Зачем:** пользователь должен видеть, почему лампа включилась, а команда — понимать ошибки.

После каждого запуска правила записывай: фактическое время, id и название правила, источник изменения, условие, действия и результат. Не нужно писать новое выполнение при каждом чтении неизменившегося датчика.

Пользовательская запись может выглядеть так:

```text
15:10:03 — Свет при протечке
Датчик под мойкой: было сухо, обнаружена вода.
Действие: включить лампу в коридоре.
Результат: выполнено локально.
Ujin: подтверждение ожидается.
```

Если одно из нескольких действий не удалось, сохранить уже выполненные действия, отметить ошибку и не выполнять оставшиеся. Нельзя написать общий успех. В первой версии не обещаем автоматический возврат оборудования в предыдущее состояние.

Сделай `GET /api/executions?limit=100`. Он возвращает последние записи. Установи разумный верхний предел `limit`, чтобы случайный запрос не выгружал весь журнал.

Ошибки и токены Ujin приходят из разных мест. Для браузера отдавай безопасное сообщение. Не возвращай полный URL с параметром token или содержимое файла доступов.

**Проверка готовности:** по записи понятно, какое условие вызвало какое действие и чем оно закончилось.

## Шаг 9 Подключить конструктор устройств

**Зачем:** форма конструктора должна создавать реальный объект, который можно использовать в правиле.

Добавить `GET /api/templates` и `POST /api/devices`. У бэкендера 1 получить список готовых шаблонов и описание универсального.

При создании принять название, семейство и список сигналов. Проверить уникальные технические имена, типы, права, начальные значения и диапазоны. У готовых физических семейств нельзя удалить сигналы, на которые рассчитывает их код. Для свободного редактирования использовать универсальный шаблон.

Согласовать с runtime создание: проверить определение, создать объект, сохранить описание. Если сохранение не удалось, убрать только что созданный объект и вернуть ошибку; не оставлять незаметное устройство, которое исчезнет после перезапуска. На время этих коротких операций использовать общую блокировку. Это небольшой откат создания, а не откат действий оборудования.

На старте сервера прочитать сохранённые определения и заново создать экземпляры. Показания могут вернуться в начальное состояние; пользовательское описание должно остаться.

Удаление устройства и изменение используемого сигнала в первом MVP можно не поддерживать. Если реализуете, запретить операцию, пока на устройство или сигнал ссылаются правила, и объяснить это пользователю.

**Проверка готовности:** через API создаётся новый `level`, его можно выбрать в правиле, симуляция 60 запускает условие `level > 50`, после перезапуска определение и правило остаются.

## Шаг 10 Организовать запуск и общий цикл

**Зачем:** устройства должны получать тики, а фоновые части — запускаться один раз и нормально останавливаться.

При старте приложения:

1. Открыть или создать структуру базы.
2. Создать общий runtime.
3. Восстановить определения устройств.
4. Загрузить правила и вычислить их исходные условия.
5. Запустить один цикл: шаг устройств примерно раз в секунду, затем проверка правил.
6. Запустить обработчик публикаций бэкендера 1, если интеграция включена.

При остановке попросить циклы завершиться и дождаться остановки. В FastAPI для действий при старте и завершении используется `lifespan`; следовать [официальному примеру](https://fastapi.tiangolo.com/advanced/events/). Это место для создания общих объектов, а не обработчик каждого HTTP-запроса.

Используйте одну общую блокировку для изменений устройств и правил. Не выполняйте запросы Ujin под этой блокировкой. Для запуска MVP — один процесс сервера. При нескольких worker каждый получит собственную память и собственные устройства, что нарушит нашу простую архитектуру.

Если браузер работает на другом адресе или порту, согласовать с фронтендером CORS — разрешение браузеру обращаться к серверу с другого origin. **Origin** — сочетание протокола, адреса и порта. Разрешить точный адрес разработки. Для итогового показа удобно отдавать сайт и API с одного адреса.

**Проверка готовности:** после двух отдельных запусков сервера устройства не дублируются, после остановки не остаются лишние циклы, запросы не ждут сетевых публикаций.

## Шаг 11 Проверить результат и передать фронтендеру

Написать небольшие проверки пользовательского поведения:

- [ ] Условие false не выполняет действие.
- [ ] Переход false → true выполняет действие один раз.
- [ ] Повтор true не запускает его заново.
- [ ] После false следующий true снова запускает действие.
- [ ] Выключенное правило не работает.
- [ ] Неизвестное устройство, read-only действие и неверный тип дают понятную ошибку.
- [ ] Ошибка одного действия отражается в журнале.
- [ ] Цикл правил останавливается, сервер не зависает.
- [ ] После перезапуска определения и правила сохранились.
- [ ] Есть один полный тест на реальных LeakSensor и Light.
