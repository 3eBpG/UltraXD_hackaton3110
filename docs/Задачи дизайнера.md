# Дизайнер

Твоя часть работы над редактором сценариев Ujin. Сначала прочитай краткий контекст ниже, затем выполняй задачи по порядку. Полный план и все зависимости: [План проекта](%D0%9F%D0%BB%D0%B0%D0%BD%20%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D0%B0.md).

Цель первого объединения: пользователь создаёт правило «протечка → включить лампу» в браузере, запускает симуляцию и видит реальное изменение эмулятора и журнал. Исходные Python-эмуляторы уже есть; интерфейс, конструктор и движок сценариев предстоит создать. Предыдущие эксперименты не используем как основу.

## 8 Подробные задачи дизайнера

### D1 Нарисовать путь пользователя

Начать с простой схемы: «Устройства → создать устройство → Сценарии → создать правило → Проверка → Журнал». Не начинать с логотипа и сложной анимации. Согласовать схему с продактом и фронтендером.

**Готово, когда:** понятно, на каком экране пользователь выполняет каждый шаг первого сценария и куда попадает после сохранения.

### D2 Сделать минимальный набор компонентов

Подготовить кнопку, текстовое поле, выпадающий список, числовое поле, переключатель, карточку устройства, индикатор состояния, сообщение об ошибке и строку журнала. У каждого интерактивного элемента показать обычное, отключённое и загрузочное состояние.

Использовать текст вместе с цветом: «Выполнено», «Ошибка», «Нет подтверждения Ujin». Не делать красный/зелёный единственным способом понять состояние. Проверить читаемый размер текста, контраст, фокус клавиатуры и подписи полей.

### D3 Спроектировать каталог и карточку устройства

В каталоге показать имя, тип, состояние и время обновления. В карточке разделить свойства, команды и настройки. Возле каждого значения дать понятную единицу измерения. Техническое имя `target_temp` можно показывать вторым уровнем; основная подпись — «Целевая температура».

Кнопки «Имитировать протечку», «Убрать воду», «Изменить температуру» поместить в отдельный блок проверки. Пользователь должен понимать, что воздействует на эмулятор.

**Готово, когда:** фронтендеру не нужно угадывать, как выглядит выключенная лампа, устаревшее значение и ошибка команды.

### D4 Спроектировать конструктор устройств

Поля: название, шаблон поведения, список сигналов. В строке сигнала: техническое имя, подпись, тип значения, группа, доступ, начальное значение, единица и диапазон при необходимости. Дать пример заполненной строки и объяснение `r/rw/w` человеческими словами.

Показать добавление и удаление строки, ошибку одинаковых имён, неверный диапазон, пустое название. Для предустановленных физических шаблонов отметить обязательные сигналы, которые нельзя удалить без нарушения поведения.

**Готово, когда:** можно создать простое устройство по макету без написания JSON вручную.

### D5 Спроектировать редактор сценариев

Форма: название; блок «Если» с устройством, сигналом, сравнением и значением; блок «То» с устройством, командой и значением. Внизу текстовая расшифровка: «Если Датчик под мойкой обнаружит воду, включить Лампу в коридоре».

Показать состояния: пустая форма, заполненная, сохранение, ошибка, включённое правило, выключенное правило. Для команды-переключателя использовать выбор «Включить/Выключить», для числа — ввод с границами, для перечисления — список. Не предлагать пользователю свободно писать имя сигнала.

### D6 Спроектировать журнал и статусы платформы

В журнале нужны время, название правила, причина, действие и итог. Отдельно показать результат локального исполнения и обмена с Ujin: «Лампа включена локально», «Запрос отправлен», «Значение подтверждено в Ujin», «Подтверждение недоступно».

Показать ошибку сети и понятное дальнейшее действие. Макет не должен автоматически превращать любую успешную локальную операцию в зелёный статус облака.

### D7 Передать макеты и проверить реализацию

Передавать экраны постепенно: каталог и редактор первыми, затем конструктор и журнал. Указать отступы, размеры, подписи и поведение. Проверить готовую версию на обычном ноутбуке и узкой ширине, чтобы кнопки и таблицы не уходили за экран.

После стабилизации интерфейса подготовить слайды по тексту продакта и реальные скриншоты прототипа. Не изображать в презентации функции, которых нет.

**Дизайнер закончил работу, когда:** все нужные экраны, ошибки и состояния реализуемы, фронтендер получил ответы, а пользователь может пройти сценарий по понятным подписям.
