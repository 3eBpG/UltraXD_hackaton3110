# Задания бэкендера 1 простыми словами

Ты отвечаешь за программные устройства и связь с Ujin. Твоя часть должна уметь создать датчик, узнать его показание, изобразить протечку, включить лампу и передать значения в платформу.

Сначала прочитай [общее объяснение бэкенда](%D0%91%D1%8D%D0%BA%D0%B5%D0%BD%D0%B4%20%D0%BF%D1%80%D0%BE%D1%81%D1%82%D1%8B%D0%BC%D0%B8%20%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D0%BC%D0%B8.md). Там разобраны устройство программы, работа эмуляторов и запросы Ujin с примерами. Этот файл — твои задания в порядке выполнения.

**Первый результат:** другой бэкендер может вызвать твою функцию, намочить датчик и включить лампу. Для этого не нужны сайт, база данных или доступный Ujin.

## Твоя часть общей архитектуры

```text
Браузер
   |
API и правила — бэкендер 2
   |
Твои функции runtime.py
   |
Объекты датчика, лампы и термостата в памяти
   |
Копии изменившихся показаний
   |
Твой ujin_adapter.py --> Ujin
```

`runtime.py` — обычный Python-файл с кодом, который управляет запущенными устройствами. Слово runtime здесь означает «устройства во время работы программы».

`ujin_adapter.py` — файл, который переводит наши имена и значения в формат внешней платформы. **Адаптер** — код-переводчик между двумя форматами.

Бэкендер 2 решает, когда должно сработать пользовательское правило. Ты предоставляешь ему способ прочитать устройство и выполнить действие. Не нужно писать второй отдельный сервер или собственный редактор правил.

## Шаг 1 Увидеть готовую лампу в работе

**Зачем:** прежде чем оборачивать библиотеку в свой код, убедиться, что понимаешь её поведение.

Из корня клонированного репозитория выполни:

```bash
cd docs/ultraxd/emulators
python3 --version
python3 -m unittest discover -s tests -v
python3 main.py light --port 8099
```

На другой машине первая команда должна указывать на её копию папки. `unittest` запускает проверки готовой библиотеки. При подготовке исходного плана в этой копии прошли 58 тестов.

Открой `http://localhost:8099` в браузере. `localhost` означает этот компьютер, `8099` — номер порта, на котором программа принимает обращения. Выбери сигнал `lamp`, введи 1 и отправь. Затем отправь 0. Остановить программу можно Ctrl+C в терминале.

Без флага `--live` это учебный локальный запуск: записи в Ujin нет. После включения мощность обновится на следующем шаге эмулятора.

Затем выполни маленький опыт «датчик → лампа» из раздела 6 общего объяснения. Открой исходные `leak_sensor.py` и `light.py`, найди `set_wet`, `tick`, `on_command`.

**Проверка готовности:** ты можешь показать `lamp=0`, затем `lamp=1`, а в опыте объяснить, почему `set_wet(True)` нужно сопровождать шагом времени.

## Шаг 2 Подключить библиотеку к общей программе

**Зачем:** сайт и правила должны работать с одними и теми же устройствами, которые живут внутри нашего сервера.

Договорись с бэкендером 2, где находится новый код. По плану библиотека копируется в `vendor/emulators`, наш код — в `backend`. Не копируй в публичный репозиторий файл доступов и PDF с паролями.

Обеспечь импорт готовых классов. В исходниках есть `from core import ...`; после переноса нужно либо исправить импорты в рабочей копии, либо один раз добавить путь библиотеки в путь поиска Python. Не меняй исходный комплект `ultraxd`, по нему мы сверяемся.

Создай класс `DeviceRuntime` в `runtime.py`. **Класс** здесь описывает набор функций и данных. Внутри него создай словарь устройств:

```python
self.devices = {
    "leak_1": LeakSensor(serial="local_leak_1", client=None),
    "light_1": Light(serial="local_light_1", client=None),
    "thermostat_1": Thermostat(serial="local_thermostat_1", client=None),
}
```

Это фрагмент будущего класса, не самостоятельная программа. `self.devices` означает «словарь, принадлежащий этому экземпляру DeviceRuntime». Строка слева — наш id, справа — объект готового эмулятора. Названия и соответствия Ujin храни отдельно от текущих показаний.

`client=None` оставляем намеренно. Так готовый `step()` не будет ждать сеть. Для Ujin позже сделаем отдельную отправку.

**Передать бэкендеру 2:** способ `runtime = DeviceRuntime()`. Он создаёт этот объект один раз при старте сервера и использует дальше.

**Проверка готовности:** два последовательных обращения к `runtime` видят одну и ту же лампу. После включения первое обращение не должно видеть 1, а второе — снова 0 из-за создания новой копии.

## Шаг 3 Дать приложению способы читать данные

**Зачем:** фронтенду нужны список устройств, описание их возможностей и текущие значения.

Напиши три функции:

- [ ] `list_devices()` — вернуть id, название и семейство каждого устройства.
- [ ] `get_state(device_id)` — собрать словарь значений из `device.signals`.
- [ ] `get_declaration(device_id)` — взять `device.declaration()` и дополнить согласованными типами значений.

Пример чтения состояния:

```python
return {name: signal.value for name, signal in device.signals.items()}
```

Это создаёт отдельный словарь, например `{"lamp": 0, "brightness": 100, "power_w": 0.0, ...}`. Не отдавай наружу сами Python-объекты Signal: браузер их не понимает.

**Описание** говорит «яркость можно менять от 1 до 100». **Состояние** говорит «яркость сейчас 70». Описание и состояние нужны вместе, но выполняют разные задачи.

Если id неизвестен, выдавай понятную ошибку `DEVICE_NOT_FOUND`. Это строковый код, по которому другой бэкендер сможет выбрать сообщение для браузера. Не возвращай пустой успешный ответ.

**Проверка готовности:** бэкендер 2 может получить состояние и список сигналов без прямого обращения к `self.devices`.

## Шаг 4 Разделить команды и симуляцию

**Зачем:** пользователь может приказать лампе включиться, а протечка является внешним событием для датчика.

Напиши `apply_command(device_id, signal_name, value)`:

1. Найти устройство по id.
2. Найти сигнал по имени.
3. Проверить, что у сигнала доступ `rw` или `w`.
4. Проверить тип и границы значения. Например, для `lamp` допустимы 0 и 1, для яркости 1–100.
5. Сохранить значения до команды в отдельный словарь.
6. Вызвать `device.handle_recv(...)` с командой.
7. Сравнить состояние после команды и вернуть результат и изменения.

Не полагайся на то, что исходный обработчик всегда сообщит об отказе через исключение: иногда он только печатает сообщение. Проверяй данные заранее.

Напиши отдельно `simulate(device_id, input_name, value)`:

- Для датчика разрешить вход `wet`: вызвать `set_wet(True)` или `set_wet(False)`.
- Для термостата разрешить тестовый вход `temperature`: установить проверенное число через `set_value`.
- Для универсального устройства позже разрешить объявленные в его описании тестовые входы.

После `wet` вернуть сообщение «воздействие принято». Показание `leak` обновится на ближайшем регулярном тике. Не запускай дополнительную секунду симуляции при каждом HTTP-запросе: иначе частые нажатия ускорят время устройства.

**Проверка готовности:** команда записать `leak=1` получает отказ, а симуляция `wet=true` меняет `leak` на 1 после тика. Команда `lamp=1` включает лампу. Неверное имя сигнала выдаёт ошибку.

## Шаг 5 Обновлять время и сообщать об изменениях

**Зачем:** датчик должен обнаружить воду, а лампа — пересчитать мощность. Движоку правил нужно узнать, что именно изменилось.

Напиши `step_all(dt)`:

1. Для каждого устройства скопировать текущие значения.
2. Вызвать `device.step(dt)`.
3. Снова собрать значения.
4. Для каждого изменившегося значения добавить словарь события в общий список.
5. Вернуть список бэкендеру 2.

Пример события:

```json
{"device_id":"leak_1","signal":"leak","old_value":0,"new_value":1}
```

В рабочем ответе добавь фактическое время. Если значение не изменилось, не создавай событие только потому, что прошла ещё одна секунда.

**Важно:** не используй `_dirty` как единственный источник событий. Это внутренний список библиотеки, который `flush()` очищает. Для первой версии проще сравнивать снимки значений до и после операции. Команды, меняющие состояние сразу, должны сравниваться аналогично в `apply_command()`.

Один общий цикл раз в секунду запускает бэкендер 2 при старте приложения. Ты предоставляешь `step_all`, но не создаёшь второй независимый бесконечный цикл в своём модуле. Оба используете одну общую блокировку состояния, описанную в общем руководстве.

**Проверка готовности:** шаг сухого датчика не создаёт новую протечку; после `wet=true` появляется событие 0 → 1; следующие шаги не создают повторных событий того же состояния.

## Шаг 6 Поддержать устройство из конструктора

**Зачем:** по кейсу пользователь должен создавать устройства, а не только смотреть заранее написанные датчик и лампу.

Бэкендер 2 передаст тебе проверенный словарь: id, название, семейство и описание сигналов. Реализуй `create_device(definition)`.

Для готового семейства выбирай класс из `REGISTRY`. Его обязательные сигналы нельзя произвольно переименовывать: код лампы ожидает сигнал `lamp`, а не любое придуманное имя.

Для нового универсального семейства сделай простой наследник `Device`. **Наследник** — класс, который использует готовые общие функции базового класса и добавляет своё поведение. Создай его сигналы через `Signal(...)`. Обычные команды меняют `rw/w`, симуляция — разрешённые читаемые значения. В первой версии допустим `tick()` без сложной физики: это устройство для ручной проверки сигналов.

Пример пользовательского устройства: название «Датчик уровня», свойство `level` от 0 до 100, управляемый переключатель `enabled`, настройка `threshold`. Честно описать поведение: `level` меняется через тестовый ввод; автоматический рост или связь с `enabled` появляется только если ты действительно её реализовал.

Не выполняй Python-код, введённый пользователем. Конструктор передаёт данные, а разрешённое поведение задаёшь ты.

**Проверка готовности:** после создания `level_sensor_1` функция `get_state()` возвращает его значения, и бэкендер 2 может использовать `level > 50` в правиле. Новое локальное устройство не объявляется автоматически созданным в Ujin.

## Шаг 7 Прочитать конфигурацию Ujin

**Зачем:** внешний API должен знать, какая квартира и какое выданное устройство относятся к нашим данным.

Прочитай на сервере локальный файл `docs/ultraxd/доступы.json`. **Конфигурация** — настройки приложения, например адрес стенда и соответствия устройств. Настройки отделяем от программной логики, чтобы не переписывать код при смене доступа.

Для каждого нашего устройства храни соответствие:

```text
наш id leak_1
  внешний id ultraxd_leak_01
  serialnumber 17048697650011143
  модель parkcloud_device
  класс integrations_devices
  квартира 2860
```

Точные значения брать из файла, не перепечатывать вручную во многих местах. Токен читать из выбранной записи резидента. Подробная расшифровка полей — в разделе 12 общего руководства.

Для первой версии публикуй только сопоставленные устройства. Если пользователь создал новый локальный датчик, а соответствия Ujin ещё нет, показывай «только локально» и пропускай облачную отправку.

Убедись, что реальные доступы не попадут в Git и браузер. Если файл уже отслеживается Git, одного добавления имени в `.gitignore` недостаточно: отдельно проверить состав отслеживаемых файлов и подготовить репозиторий без секретов.

**Проверка готовности:** можно показать таблицу соответствий без токенов и прочитать параметры клиента, не выводя пароли.

## Шаг 8 Отправить одно показание и проверить его

**Зачем:** доказать реальный обмен с Ujin на маленьком понятном примере.

Сначала выполнить пример клиента из общего руководства с `dry_run=True`. Он покажет сформированный пакет без сетевой записи. Затем определить доступный способ чтения значения обратно и отдельно включить реальную отправку для своего устройства.

Первым отправить ненулевой `battery=95` датчика. Не начинать с нового прибора, нового сигнала, нуля и нескольких устройств одновременно: иначе непонятно, какая часть мешает.

Проверить:

- [ ] `base_url` без завершающего `/api` для этой библиотеки.
- [ ] UAE-авторизация: ust и квартира в query-параметрах.
- [ ] В теле `sn` содержит внешний id, `s` — полное имя сигнала, `c` — класс модели.
- [ ] Тело отправляется как JSON.
- [ ] Для нового словаря проверены обе фазы создания и записи.
- [ ] Полученный ответ относится к реальному запросу, а не к dry-run.
- [ ] Значение видно отдельным чтением или в панели организаторов.

Возвращай статус `accepted`, если есть только успешный ответ на отправку. Статус `verified` ставь после независимого подтверждения. Если чтение требует сотрудника, обратись к продакту за уточнением доступа. Не меняй роли и чужие привязки наугад.

**Проверка готовности:** можешь показать собственное отправленное значение и отдельное подтверждение на стороне Ujin. Если подтверждения нет, можешь точно объяснить, на каком шаге остановился.

## Шаг 9 Сделать отправку устойчивой

**Зачем:** медленный интернет не должен останавливать симуляцию и сайт.

Создай одну очередь публикаций и один фоновый обработчик. Очередь содержит копии простых данных: id устройства, имя сигнала, значение, время/версию. Не передавай туда живой объект эмулятора, который параллельно меняется.

Для MVP можно хранить последнее ожидающее значение каждой пары «устройство + сигнал». Если за время отправки появилась новая версия значения, не удаляй её при завершении старого запроса. Сравнивай номер версии или сохранённую отметку задания.

Обработчик получает копию задания, отпускает блокировку очереди и выполняет запрос с таймаутом. После ошибки сохраняет статус и делает повтор с паузой. На старте и после восстановления связи отправляет актуальный снимок. Не обещаем сохранение каждого промежуточного события при долгом отсутствии сети.

Фильтруй отправляемые сигналы: только поддерживаемые показания `r/rw`, не команды `w`, и не текстовый `fw` в числовой канал. Преобразование нуля делать на границе отправки, не в локальных данных.

Обратный приём команд из Ujin подключать отдельным этапом, если доступны права. Запоминать задачу как выполненную только после успешного применения. Не считать облачное старое показание управляющей командой.

**Проверка готовности:** при выключенном интернете локальный датчик всё ещё включает лампу через правило, на сайте видна ошибка Ujin, после восстановления есть новая попытка отправки.

## Шаг 10 Сдать свою часть другому бэкендеру

Передай один небольшой документ с командами запуска и примерами вызовов твоих функций. Укажи, какие методы существовали в библиотеке, а какие добавил ты.

Сделай сброс демо: сухой датчик, выключенная лампа, согласованные настройки термостата. Бэкендер 2 должен временно приостановить правила на время сброса и затем заново запомнить исходные условия.

Вместе пройти:

- [ ] Список и описание устройств читаются через твои функции.
- [ ] Команда лампе работает и возвращает фактическое состояние.
- [ ] Read-only сигнал нельзя менять обычной командой.
- [ ] Симуляция воды работает через отдельную операцию.
- [ ] Новые показания выдаются как события.
- [ ] Конструктор создаёт действующее локальное устройство.
- [ ] Сброс позволяет повторить демонстрацию.
- [ ] Статус Ujin соответствует имеющимся доказательствам.
- [ ] Ошибка сети не ломает устройства.

**Не брать в первое демо:** выключение реле водяного счётчика из стартового пакета. В исходной проверке оно падает с `KeyError: 'power_w'`. Если потребуется водяной сценарий, сначала исправить и проверить модель. Генератор `new_device.py --clone light` сам по себе тоже не создаёт физику клапана.

## Что показать через первые два часа

Один общий объект runtime с датчиком и лампой. Вызов `simulate("leak_1", "wet", True)`, затем `step_all(1)` даёт событие протечки. Вызов `apply_command("light_1", "lamp", 1)` включает лампу. Бэкендер 2 получил точный формат этих функций и может соединить их с API и правилом.
