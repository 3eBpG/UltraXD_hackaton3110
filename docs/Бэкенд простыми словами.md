# Бэкенд проекта простыми словами

Этот текст нужно прочитать обоим бэкендерам. Он объясняет, какую программу мы собираем, как работают готовые эмуляторы, откуда берутся данные и как подключается Ujin. После него каждый выполняет свой файл заданий.

**Результат работы:** человек открывает сайт, создаёт правило «Если обнаружена вода, включить лампу», нажимает «Имитировать протечку» и видит включившуюся лампу и объяснение в журнале. Затем мы показываем, что данные устройства дошли до Ujin.

Ниже описана предлагаемая архитектура будущего приложения. Готовые классы эмуляторов и `UjinClient` уже есть в исходном пакете. Наши файлы `runtime.py`, `scenario_engine.py`, маршруты `/api/devices` и остальные части приложения ещё нужно написать. Состояние внешнего стенда по этой инструкции не проверено. Прошлые эксперименты не используются.

## 1 Что такое бэкенд в нашем случае

**Фронтенд** — часть приложения, которую человек видит в браузере: кнопки, списки и формы. **Бэкенд** — программа, которая получает запросы от этих кнопок, хранит данные и выполняет действия.

Например, кнопка «Включить лампу» сама не умеет управлять эмулятором. Браузер отправляет серверу сообщение: «Для устройства light_1 установить lamp=1». Сервер проверяет запрос, меняет устройство и возвращает результат. После этого браузер рисует включённую лампу.

**Сервер** здесь не обязательно отдельный мощный компьютер. На хакатоне это может быть Python-программа, запущенная на вашем ноутбуке. Когда вы остановите программу, запросы к ней перестанут работать.

**API** — набор заранее согласованных способов обратиться к программе. Например: «дай список устройств», «сохрани правило», «включи лампу». У каждого такого способа есть адрес и формат данных.

В проекте два разных API:

| API | Кто его делает | Кто к нему обращается | Для чего |
| --- | --- | --- | --- |
| Наш API | Бэкендер 2 | Браузер | Показать устройства, сохранить сценарий, запустить симуляцию |
| API Ujin | Организаторы | Наш сервер, через код бэкендера 1 | Передать показания в платформу, прочитать доступные данные, получить команды при наличии прав |

Браузеру не нужны пароли и токены Ujin. Он общается с нашим сервером. Наш сервер уже знает, как обращаться к платформе.

## 2 Общая схема программы

Для этого плана выбираем **один Python-сервер**. Оба бэкендера пишут разные файлы одной программы и запускают её вместе. Между их файлами используются обычные вызовы Python-функций.

```text
Пользователь в браузере
          |
          | HTTP-запрос: например, «создай правило»
          v
Наш API — app.py — бэкендер 2
          |
          +--> storage.py: сохранить устройства и правила в SQLite
          |
          +--> runtime.py: узнать или изменить состояние устройства
          |       |
          |       +--> готовые объекты LeakSensor, Light, Thermostat
          |
          +--> scenario_engine.py: проверить «если» и выполнить «то»
                  |
                  +--> runtime.py: отправить команду нужному устройству

Изменения устройств --> очередь отправки --> ujin_adapter.py --> Ujin
                           бэкендер 1           бэкендер 1

Результаты выполнения --> storage.py --> журнал в браузере
```

**SQLite** — база данных в одном файле, например `data/app.db`. В неё записываем то, что нельзя потерять после выключения программы: созданные устройства, сценарии и журнал. Отдельный сервер базы для этого не нужен.

Для HTTP-части предлагаем **FastAPI**: библиотеку Python, в которой удобно описывать адреса запросов и проверять входные данные. Это выбор для нашего небольшого приложения. Если команда уже начала на другом знакомом фреймворке, переносить только ради названия не нужно. Первый маршрут и запуск объяснены в [официальном руководстве FastAPI](https://fastapi.tiangolo.com/tutorial/first-steps/).

## 3 Кто что делает

**Бэкендер 1 отвечает за устройства:** создать датчик в памяти, прочитать его состояние, намочить его в симуляции, включить лампу, выполнить шаг времени и отправить показания в Ujin.

**Бэкендер 2 отвечает за приложение:** принять запрос браузера, проверить данные формы, сохранить сценарий, заметить выполнение условия, попросить бэкендера 1 включить лампу и записать итог.

Пример разговора между частями кода:

```python
# Код бэкендера 2:
state = runtime.get_state("leak_1")

# Если сохранённое пользователем правило сработало:
result = runtime.apply_command("light_1", "lamp", 1)
```

`runtime` — объект, который создаст бэкендер 1. `get_state` и `apply_command` — договорённые функции, которые тоже предстоит написать. Они скрывают внутреннее устройство эмуляторов от остального приложения.

Один раз создаём общий объект `runtime` при запуске сервера. Не создаём новый датчик внутри каждого HTTP-запроса: иначе каждый запрос будет видеть новую сухую копию датчика.

## 4 Что такое эмулятор

Эмулятор — программа, которая ведёт себя как устройство. Реальной лампы на столе нет, но у программы есть значения «включена», «яркость» и «потребляемая мощность». При включении эмулятор меняет эти значения по написанным правилам.

В Python **класс** описывает устройство такого типа. **Объект** — один конкретный экземпляр класса. Класс `Light` — описание светильника. `Light(...)` — создание одного светильника в памяти.

```python
from devices.light import Light

lamp = Light(serial="local_light_1", client=None)
```

`lamp` — переменная, в которой хранится ссылка на этот экземпляр. `serial` здесь служит меткой для учебного локального устройства. `client=None` означает, что мы не подключили к нему клиент внешней платформы.

Две команды `Light(...)` создадут две разные лампы. Если включить первую, вторая сама по себе не включится.

### Сигнал — отдельное значение устройства

У лампы есть словарь `signals`. **Словарь Python** хранит пары «ключ → значение». Ключом здесь служит имя сигнала, например `lamp`, а значением — объект с описанием и текущим показанием.

```python
lamp.signals["lamp"].value       # 0: выключено, 1: включено
lamp.signals["brightness"].value # яркость, например 100
lamp.signals["power_w"].value    # мощность в ваттах
```

У датчика протечки:

| Сигнал | Значение | Кто его меняет |
| --- | --- | --- |
| `leak` | 0 — сухо, 1 — обнаружена вода | Сам эмулятор по состоянию «мокро/сухо» |
| `battery` | Заряд в процентах | Эмулятор постепенно уменьшает заряд |
| `tamper` | Состояние вскрытия корпуса | Логика устройства или отдельная симуляция, если её реализовать |
| `self_test` | Команда самотеста | Пользователь или сценарий отправляет команду |

### Почему не во все сигналы можно писать

У сигнала есть поле `management`, то есть разрешённый способ обращения:

- `r` — можно читать. Например, датчик сообщает температуру.
- `rw` — можно читать и менять командой. Например, включённость лампы.
- `w` — можно отправить действие. Например, «выполнить самотест».

**Свойство** — то, что измеряется или сообщается. **Возможность** — то, чем можно управлять. **Настройка** — параметр работы, например время автоматического выключения.

Группа помогает нарисовать интерфейс. Разрешение `management` помогает решить, допустима ли команда. Это связанные, но разные поля.

## 5 Как эмулятор выполняет время и команды

### Шаг времени

Эмуляторы не меняются сами по себе. Кто-то должен вызывать функцию, которая означает «прошла ещё одна секунда симуляции»:

```python
device.step(1)
```

**Тик** — один такой шаг. Число `1` — величина шага внутри модели, а не команда Python подождать одну секунду. Если вызвать `step(1)` сто раз подряд, модель пройдёт сто шагов очень быстро. Чтобы она работала примерно в реальном времени, наш сервер вызывает её раз в секунду.

В исходном коде `step(1)` делает три вещи:

1. Увеличивает счётчик шагов `tick_count`.
2. Вызывает `tick(1)` — правила поведения конкретного устройства.
3. Вызывает `flush()` — собирает изменившиеся сигналы и, если клиент подключён, передаёт их ему.

Например, у включённой лампы `tick()` пересчитает мощность и накопленную энергию. У датчика протечки проверит, мокрый ли датчик, и уменьшит заряд батареи. Это упрощённые модели, достаточные для демонстрации поведения.

### Команда устройству

Для команды используем штатный обработчик `handle_recv`, который проверяет наличие сигнала и право записи, а затем вызывает реакцию устройства `on_command`:

```python
lamp.handle_recv({
    "recv": [{
        "command": "management",
        "id": lamp.serial,
        "lamp": 1
    }]
})
lamp.step(1)
```

Смысл этого словаря: «вот список полученных команд; команда управления для этой лампы; установить сигнал lamp в 1».

После команды `lamp` меняется сразу. После шага обновляются связанные измерения, например `power_w`. Не заменяйте команды повсеместным присваиванием `signal.value = ...`: так можно пропустить реакцию устройства и таймеры.

Штатный `handle_recv()` в некоторых случаях только печатает отказ и не возвращает структурированную ошибку. Поэтому наша функция `apply_command()` должна сама проверить устройство, сигнал и значение до вызова. Нельзя возвращать браузеру «успех» только потому, что Python не выбросил исключение.

### Воздействие на симуляцию

В реальности воду создаёт внешняя ситуация. В эмуляторе её задаём специальной функцией:

```python
sensor.set_wet(True)  # True означает «да, датчик мокрый»
sensor.step(1)       # датчик вычисляет своё новое показание
```

Это изменит `leak` на 1. Обычная команда записать `leak=1` недопустима: `leak` доступен только для чтения. Поэтому в нашем API две разные операции: «команда устройству» и «воздействие на симуляцию».

## 6 Первый опыт без сайта и без Ujin

Команду ниже можно выполнить из терминала целиком, находясь в корне клонированного репозитория. Она использует только исходные Python-классы и не обращается к интернету. Это учебная проверка последовательности, а не готовый движок пользовательских сценариев.

```bash
cd docs/ultraxd/emulators
python3 - <<'PY'
from devices.leak_sensor import LeakSensor
from devices.light import Light

sensor = LeakSensor(serial="local_leak_1", client=None)
lamp = Light(serial="local_light_1", client=None)

print("До:", sensor.signals["leak"].value, lamp.signals["lamp"].value)

sensor.set_wet(True)
sensor.step(1)

if sensor.signals["leak"].value == 1:
    lamp.handle_recv({"recv": [{
        "command": "management", "id": lamp.serial, "lamp": 1
    }]})

lamp.step(1)
print("После:", sensor.signals["leak"].value, lamp.signals["lamp"].value)
print("Мощность:", lamp.signals["power_w"].value)
PY
```

Ожидаем: строка `До: 0 0`, затем `После: 1 1`, мощность `12.0` при исходной яркости 100. Между ними возможны служебные сообщения устройства. Они нормальны.

В этом опыте правило написано прямо в Python. В приложении бэкендер 2 должен читать условие и действие из сохранённых пользовательских данных. Именно это позволяет человеку создавать разные сценарии через форму.

## 7 Описание устройства и его состояние

У каждого устройства есть две разные части данных.

**Описание, или декларация:** какие сигналы существуют, как называются, что означают, что можно менять, каковы единицы и диапазоны.

**Состояние:** какие значения у сигналов сейчас.

```python
description = lamp.declaration()
state = {name: signal.value for name, signal in lamp.signals.items()}
```

Вторая строка означает: «пройти по всем сигналам и собрать новый словарь из их имён и текущих значений».

Описание меняется редко. Состояние может меняться каждую секунду. Браузеру нужно и то и другое: по описанию он создаёт переключатель яркости, а из состояния узнаёт, какое число показать.

В исходной декларации есть `name`, `title`, `control`, `management`, `kind`, `group` и иногда `min`, `max`, `measure`, `layout`. Текущего значения в ней нет. Универсального поля типа значения тоже нет: его добавим в наш API как `value_type`, например `integer`, `number`, `string`.

Не определяйте тип только по текущему значению: температура 20 всё равно может быть дробной. Для готовых шаблонов задайте типы явно один раз. Для устройства из конструктора пользователь выбирает их в форме.

## 8 Откуда брать данные

| Данные | Откуда берём | Где держим в приложении | Кто отвечает |
| --- | --- | --- | --- |
| Какие семейства уже реализованы | `emulators/devices/__init__.py`, словарь `REGISTRY` | В коде списка шаблонов | Бэкендер 1 |
| Какие сигналы есть у готового устройства | `device.declaration()` | Получаем из runtime и дополняем типами | Бэкендер 1 |
| Текущее значение протечки, света, температуры | `device.signals[name].value` | В памяти экземпляра эмулятора | Бэкендер 1 |
| Название нового устройства и его сигналы | Форма конструктора в браузере | Сохраняем в SQLite, затем создаём экземпляр | Бэкендер 2 сохраняет, бэкендер 1 создаёт |
| Пользовательские условия и действия | Форма редактора | SQLite | Бэкендер 2 |
| Доступы, квартира и выданные облачные устройства | Локальный `docs/ultraxd/доступы.json` | Только серверная конфигурация | Бэкендер 1 |
| Подтверждение, что значение дошло до Ujin | Отдельное чтение API с подходящей ролью или панель организаторов | Отдельный статус доставки | Бэкендер 1 |
| История выполнения наших правил | Создаём сами во время выполнения | SQLite | Бэкендер 2 |

Для локальных эмулируемых устройств **источником текущего состояния служит эмулятор**. Ujin получает его показания. Не читайте старое облачное значение обратно и не записывайте его поверх нового локального состояния. Обратная управляющая команда — отдельное событие, которое нужно распознать и применить.

Пример: лампа уже включена локально, а Ujin ещё показывает старое 0. В интерфейсе показываем «локально включена; подтверждение Ujin ожидается». Не выключаем лампу только потому, что облако ещё не обновилось.

### Что переживает перезапуск

Память программы исчезает после остановки. Файл SQLite остаётся. Поэтому сохраняем определения устройств, сценарии и журнал. В первой версии допускаем, что показания и таймеры эмуляторов при запуске возвращаются в начальное состояние. Это нужно написать в интерфейсе и инструкции.

На старте: открыть базу → прочитать определения → создать по ним объекты устройств → загрузить правила → запустить один цикл времени. Не создавать одинаковые демо-устройства снова при каждом старте.

## 9 Как разложить файлы

Следующая структура — предложение для нового кода в репозитории команды. Папка `backend` пока не создана этим документом.

```text
backend/
  __init__.py           позволяет импортировать папку как Python-пакет
  app.py                HTTP-адреса, запуск и остановка программы
  schemas.py            проверка формы устройства, правила и команды
  runtime.py            список живых объектов устройств и работа с ними
  scenario_engine.py    проверка условий и выполнение действий
  storage.py            запись и чтение SQLite
  ujin_adapter.py       перевод наших данных в формат Ujin и отправка
  config.py             чтение настроек и доступов на сервере
vendor/
  emulators/            копия исходной библиотеки организаторов
data/
  app.db                локальная база, создаётся приложением
tests/
  ...                   проверки поведения
```

**Модуль** — обычный файл Python. **Пакет** — папка модулей, которые можно импортировать. `vendor` означает «чужой код, который мы используем как библиотеку». Скопировать нужно именно библиотеку эмуляторов, без брошюры с паролями и файла доступов.

В исходниках используются импорты вроде `from core import Device`. Простое перемещение папки может сломать их. Бэкендер 1 должен выбрать один способ подключения: исправить импорты в рабочей копии на пакетные либо один раз добавить абсолютный путь к `vendor/emulators` в Python-путь при запуске приложения. Для быстрого прототипа второй способ проще; вычислять путь от расположения файла, а не от случайной текущей папки терминала. Исходный `ultraxd` оставить эталоном.

## 10 Как части программы работают вместе

Бэкендеры сначала договариваются о функциях. Это называется **контрактом**: «что передаём на вход и что ожидаем на выходе».

| Функция бэкендера 1 | Простое значение | Пример результата |
| --- | --- | --- |
| `list_devices()` | Какие устройства запущены | Список id, названий и семейств |
| `get_state("light_1")` | Какие значения сейчас | `{"lamp": 0, "brightness": 100, ...}` |
| `get_declaration("light_1")` | Какие сигналы разрешены | Список описаний сигналов |
| `apply_command("light_1", "lamp", 1)` | Включить лампу | `{"ok": true, "state": {...}, "changes": [...]}` |
| `simulate("leak_1", "wet", True)` | Намочить датчик | Принятое воздействие; показание изменится на ближайшем тике |
| `step_all(1)` | Дать всем устройствам один шаг | Список изменений |
| `create_device(definition)` | Создать экземпляр по описанию | Id и состояние нового устройства |
| `reset_demo()` | Вернуть исходное состояние | Снимок после сброса |

`changes` — обычный список словарей. Один элемент выглядит так:

```json
{
  "device_id": "leak_1",
  "signal": "leak",
  "old_value": 0,
  "new_value": 1,
  "timestamp": "2026-10-31T10:00:00Z"
}
```

Это **событие**: описание того, что изменилось. Время здесь пример; в программе записываем фактическое. Внутри сервера удобно использовать UTC, а браузер показывает локальное время пользователя.

Бэкендер 1 отдаёт события, бэкендер 2 проверяет по ним правила. Непосредственный вызов команды тоже может изменить состояние: такие изменения нужно передавать тем же способом, а не ждать, что следующий тик обязательно их обнаружит.

### Порядок одного прохода программы

1. Под общей блокировкой выполнить шаг устройств и собрать изменения.
2. По этим изменениям проверить правила.
3. Применить действия и проверить изменения от них. Ограничить цепочку, чтобы два правила не запускали друг друга бесконечно.
4. Подготовить записи журнала и копии значений для отправки.
5. Освободить блокировку.
6. Сохранить журнал короткой операцией базы. Передать копии значений в очередь отправки Ujin.

**Блокировка** — средство Python, которое не позволяет двум участкам программы одновременно менять общие данные. Для этого проекта можно использовать один `threading.RLock` вокруг состояния устройств и правил. Важно договориться об одной общей блокировке, а не завести две независимые.

**Очередь** — место, куда кладём задания «отправить такое значение». **Фоновый обработчик**, или worker, забирает задания и общается с Ujin. Пока он ждёт интернет, устройства и HTTP-запросы продолжают работать. Для первой версии хватит одного такого обработчика в том же процессе, без Redis и отдельного сервиса.

Сетевые вызовы не выполнять под блокировкой состояния. Иначе пятисекундное ожидание Ujin остановит локальные команды.

## 11 Как проходит одна протечка от начала до конца

1. Пользователь сохраняет правило. Браузер отправляет JSON нашему API.
2. Бэкендер 2 проверяет: датчик существует, `leak` читается, лампа существует, в `lamp` можно писать значение 1.
3. Бэкендер 2 сохраняет правило в SQLite и включает его в список активных правил.
4. Пользователь нажимает «Имитировать протечку». Браузер вызывает наш `/api/devices/leak_1/simulate`.
5. API вызывает функцию runtime. Она находит уже существующий объект датчика и вызывает `set_wet(True)`.
6. На ближайшем тике датчик меняет `leak` с 0 на 1.
7. Runtime выдаёт событие изменения. Движок правил сравнивает новое значение с условием.
8. Условие выполнено. Движок вызывает `apply_command("light_1", "lamp", 1)`.
9. Эмулятор лампы применяет команду. В журнал записывается, какое правило сработало и что сделало.
10. Адаптер получает отдельные задания публикации новых значений в Ujin.
11. Браузер читает наш API и показывает текущую лампу, журнал и статус облачной отправки.

Если интернет пропал на шаге 10, лампа уже включена. В журнале локальное выполнение успешно, а у интеграции отдельная ошибка. Одно не подменяет другое.

## 12 Как работает API Ujin

### Из чего состоит запрос

Запрос — сообщение внешнему серверу. У него есть:

- **Метод**, например GET — получить данные, POST — отправить данные или выполнить действие.
- **Адрес**, например путь к чтению карточки устройства.
- **Query-параметры** — значения после знака `?` в адресе.
- **Тело** — данные внутри запроса, например JSON с показаниями.
- **Заголовки** — описание сообщения, например `Content-Type: application/json` означает, что в теле JSON.

**JSON** — текст с объектами, списками, строками и числами. Он похож на словарь Python, но это отдельный формат: в JSON пишут `true`, в Python — `True`.

**Токен** — секретная строка, которая подтверждает право обращения. Она не является id устройства. Разные токены могут иметь разные права.

### Где взять доступы

В исходном `docs/ultraxd/доступы.json` есть:

| Поле | Что означает |
| --- | --- |
| `api_base` | База адресов API стенда |
| `residents` | Аккаунты жильцов; у каждого есть логин, пароль, `ust` и квартира |
| `employee` | Данные сотрудника; для чтения может понадобиться отдельный вход этой ролью |
| `devices` | Выданные устройства и соответствия их идентификаторов |
| `team_apartment` | Квартира команды |
| `cos_token` | Другой тип токена, для consumer-доступа; это не замена ust во всех методах |

Для публикации UAE брошюра команды предлагает **ust резидента плюс id квартиры**. Общие примеры с dev-токеном относятся к другому пути авторизации. Начинаем с пути своей брошюры.

Токен `ust` можно получить входом через `POST /api/auth/authenticate/` с логином и паролем; справочник пакета указывает ответ `data.token`. При входе сотрудником параметры роли уточнить по выданным данным и ответу организаторов. Сам факт наличия логина сотрудника ещё не подтверждает доступ к конкретному устройству.

Не выводить весь файл доступов в терминал во время демонстрации. В документах и примерах используем заглушки, в программе читаем реальный файл на сервере.

### Не путайте три имени одного устройства

| Значение | Пример датчика | Где используется |
| --- | --- | --- |
| Наш id | `leak_1` | В нашем API, SQLite и сценариях |
| `ext_guid`, в JSON доступов поле `ext` | `ultraxd_leak_01` | В теле публикации Ujin, поле `sn` |
| Серийный номер, в JSON доступов поле `sn` | `17048697650011143` | При чтении карточки Ujin, параметр `serialnumber` |

Название `sn` используется в разных местах с разным смыслом. Поэтому не переносить значение из одного запроса в другой по совпадению названия поля. Длинный серийный номер передавать в браузер строкой, чтобы JavaScript не округлил его.

Есть ещё **модель** `parkcloud_device` и **класс публикации** `integrations_devices`. Это разные значения. Поле `c` тела публикации должно содержать класс.

### Как отправить показание

Для готового датчика тело запроса имеет такой вид:

```json
{
  "data": [
    {
      "sn": "ultraxd_leak_01",
      "s": "integrations_devices_battery",
      "v": 95,
      "c": "integrations_devices"
    }
  ]
}
```

Расшифровка: `data` — список показаний; `sn` — внешнее имя устройства; `s` — имя сигнала в Ujin; `v` — новое значение; `c` — класс устройства.

Адрес метода: `POST /api/import_device/group-update-device-signal/`. Для UAE авторизация передаётся в query как `token` и `apartment_id`.

Важная особенность именно выданного Python-клиента: `_post_json()` берёт `sn` первой строки и передаёт его ещё и в query-параметре `serialnumber`. Поэтому при таком пути отправляйте отдельный пакет на одно устройство. Это поведение исходного клиента, а не правило, которое можно угадать по названию параметра. Если стенд отклоняет запрос, передайте организаторам пример без секретов; не подставляйте разные id наугад.

### Как воспользоваться готовым клиентом без сетевой записи

Этот пример запускается из папки `docs/ultraxd/emulators`. Он читает доступы, собирает правильный формат и **не отправляет запрос в сеть**, потому что `dry_run=True`.

```python
import json
from pathlib import Path
from ujin_client import UjinClient

access = json.loads(Path("../доступы.json").read_text())
resident = access["residents"][0]
device = next(d for d in access["devices"] if d["family"] == "leak")

api_base = access["api_base"].rstrip("/")
base_url = api_base[:-4] if api_base.endswith("/api") else api_base

client = UjinClient(
    base_url=base_url,
    device_token="",
    dry_run=True,
    ust=resident["ust"],
    apartment_id=resident["apartment_id"],
    cls=device["publish_class"],
    signal_prefix=device["publish_class"] + "_",
    logger=lambda message: None,
)

result = client.publish_group([{
    "sn": device["ext"],
    "s": device["publish_class"] + "_battery",
    "v": 95,
    "c": device["publish_class"],
}])
print("Учебный режим:", result.get("dry_run"))
```

`next(...)` находит первую запись семейства leak. `base_url` нужен без завершающего `/api`, потому что клиент добавит `/api/...` сам. `logger=lambda message: None` отключает обычный вывод клиента; отдельные строки JOURNAL с данными публикации всё ещё возможны, в этом примере в них нет токена.

Для реальной записи бэкендер 1 отдельно переключает проверенный код на `dry_run=False`, проверяет доступы и работает только с выданными устройствами. До этого определяет, как прочитать значение обратно. Изменение флага не доказывает, что на стенде есть все нужные разрешения.

### Если сигнал ещё не создан в Ujin

По контракту пакета новый сигнал публикуется в две фазы: сначала короткое имя `battery`, затем полное `integrations_devices_battery`. Первая фаза создаёт запись в словаре сигналов платформы; вторая записывает значение по полному имени.

Не создавайте словари заново при каждом тике. Сначала выясните, какие уже доступны. Метод `publish_group(rows, new_short=...)` в исходном клиенте умеет отправить две фазы, но игнорирует ответ первой фазы. Для надёжного статуса нужно изменить рабочую копию адаптера так, чтобы он проверял оба ответа и не продолжал при ошибке создания.

### Особенность значения 0

Пакет предупреждает, что стенд может не записывать числовой ноль, и использует обход `0 → 0.001` при отправке. Внутри приложения значения остаются правильными: лампа выключена — 0, протечки нет — 0.

Преобразование выполняется только на границе с Ujin. При чтении обратно нельзя просто считать любое ненулевое число истиной: `0.001` для такого переключателя означает отправленный ноль. Для дробных измерений вроде энергии `0.001` может быть настоящим значением. Нормализация зависит от описания конкретного сигнала.

Для первой проверки возьмите ненулевую батарею 95, чтобы отдельно проверить адрес, авторизацию и имена. Затем проверьте 0/1 на согласованном двоичном сигнале.

### Как проверить результат отправки

Условный запрос чтения карточки:

```text
GET https://api-uae-test.ujin.tech/api/bmsdevice/get-device-info/
    ?token=<ТОКЕН_С_ПРАВОМ_ЧТЕНИЯ>
    &serialnumber=17048697650011143
```

Это схема одного URL, переносы добавлены для чтения. Здесь используется длинный серийный номер, не ext_guid.

Брошюра команды предупреждает об ограничении чтения ролью сотрудника. Если резиденту отказано, не считать это доказательством, что публикация не сработала. Нужен доступный способ независимого чтения: подходящая роль или панель организаторов.

Проверяйте четыре вещи: то ли устройство, тот ли сигнал, то ли значение, достаточно ли свежая запись. Локальная память эмулятора не является подтверждением Ujin.

| Статус | Значение |
| --- | --- |
| `disabled` | Отправка выключена |
| `pending` | Значение ждёт отправки или повторной попытки |
| `accepted` | API ответил без ошибки, но сохранение ещё не подтверждено |
| `verified` | Отдельное чтение подтвердило значение |
| `failed` | Запрос или проверка закончились ошибкой; причина записана |

При новой локальной версии показания старый `verified` нельзя оставлять как подтверждение новой версии. Связывайте статус с конкретным отправленным значением и временем.

### Как команды могут приходить из Ujin

Команда вниз означает: человек изменил что-то в интерфейсе Ujin, и наше устройство должно исполнить это изменение. В пакете описаны polling, HTTP-вызов устройства и WebSocket.

**Polling**, или опрос, — наш сервер периодически спрашивает платформу, есть ли новая задача. **WebSocket** — постоянное соединение для сообщений. Для первого MVP не нужно реализовывать все способы сразу.

Если опрос разрешён, читаем карточку и ищем именно задачу, а не обычное измеренное значение. В примерах клиента задача находится в `task` или `state.task`; документация также упоминает `signal_task_value`. Формат нужно сверить с реальным ответом доступной роли.

У задачи запоминаем время или id, например `task_dt`. Это позволяет отличить новую команду от повторного чтения старой. Запоминать выполнение нужно после успешного применения, иначе неудачная команда будет ошибочно считаться выполненной.

Для команд требуется разрешение `rw/w` в словаре платформы. Локальное `rw` в Python само по себе не меняет облачный словарь. Если организаторы выдали облачное `r`, это исправляется с их стороны. Наш локальный движок в это время продолжает работать.

### Что делать с облачными сценариями autoscripts

Ujin также имеет собственные методы сценариев. Они могут пригодиться позже, но доступность сигналов и исполнения нужно подтвердить. В файлах пакета расходятся названия полей создания сценария, поэтому не стоит строить всю первую версию вокруг непроверенного запроса.

В нашем плане правило исполняется на нашем сервере, а Ujin получает данные. Продакт должен уточнить у организаторов, достаточно ли этого для зачёта интеграции или требуется исполнение именно в Ujin. Если требуется облачное исполнение, это отдельная обязательная задача, которую нельзя заменить локальной демонстрацией.

## 13 Как не зависнуть при ошибках

Если публикация не работает, проверять по порядку:

1. Правильный ли стенд и нет ли `/api/api/` в URL.
2. Не остался ли `dry_run=True`.
3. Подходит ли роль токена этому действию.
4. Есть ли квартира в query для режима UAE.
5. Используется ли ext_guid в теле публикации и нужный serialnumber в чтении.
6. Правильны ли класс `c`, полное имя `s` и JSON-тело.
7. Создан ли словарь сигнала и не отправляется ли неподдерживаемый тип.
8. Не маскирует ли особенность нуля результат.
9. Есть ли независимое подтверждение, а не только `error=0`.

Через 20–30 минут без результата собрать один понятный пример: время, свой прибор, путь метода, тело без секретов, безопасное сообщение об ошибке, что ожидали. Передать продакту для организаторов. Продолжать разработку устройств и правил локально.

У сетевого запроса должен быть **таймаут** — предел ожидания, например 5 секунд. После ошибки программа должна продолжать жить. Повтор отправлять с паузой, например 2, 5, 10 секунд, затем не чаще одного раза в 30 секунд. Это наш простой план повторов, не требование Ujin.

Для MVP очередь может хранить только последнее неотправленное значение каждого сигнала. Если за время отсутствия сети батарея изменилась несколько раз, отправляем актуальное значение. Это не гарантирует доставку каждого промежуточного события; такую гарантию не заявляем.

## 14 Первые совместные проверки

- [ ] Оба человека выполнили учебный пример протечки и могут объяснить каждую его часть.
- [ ] Бэкендер 1 создал функции чтения, команды и симуляции.
- [ ] Бэкендер 2 вызвал эти функции через HTTP, не создавая новые устройства на каждый запрос.
- [ ] Правило сохранено как данные и применяется без отдельного Python-if для каждого устройства.
- [ ] Повторное чтение `leak=1` не включает лампу заново каждую секунду.
- [ ] После выключения правила новая протечка не запускает действие.
- [ ] После перезапуска сохранённые определения и правила не потерялись.
- [ ] Новое устройство из конструктора создаётся локально и участвует в правиле. Оно не объявлено автоматически зарегистрированным в Ujin.
- [ ] Обрыв интернета не останавливает локальный сценарий.
- [ ] Для показанного статуса `verified` есть реальное независимое подтверждение Ujin.
