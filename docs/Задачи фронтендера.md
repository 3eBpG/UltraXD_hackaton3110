# Фронтендер

Твоя часть работы над редактором сценариев Ujin. Сначала прочитай краткий контекст ниже, затем выполняй задачи по порядку. Полный план и все зависимости: [План проекта](%D0%9F%D0%BB%D0%B0%D0%BD%20%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D0%B0.md).

Цель первого объединения: пользователь создаёт правило «протечка → включить лампу» в браузере, запускает симуляцию и видит реальное изменение эмулятора и журнал. Исходные Python-эмуляторы уже есть; интерфейс, конструктор и движок сценариев предстоит создать. Предыдущие эксперименты не используем как основу.

## 9 Подробные задачи фронтендера

### F1 Подготовить приложение и слой API

Сделать четыре раздела: «Устройства», «Конструктор», «Сценарии», «Журнал». Организовать обращения к серверу в одном модуле, чтобы URL и обработка ошибок не были размазаны по компонентам. Получить от бэкендера 2 примеры ответов из раздела 12.

До готовности сервера использовать примеры JSON с теми же полями. Помечать этот режим как демонстрационные данные. После подключения заменить источник целиком, чтобы часть экрана не оставалась на старых заглушках.

**Готово, когда:** приложение открывается, разделы доступны, ошибку API можно показать пользователю.

### F2 Сделать список и карточку устройства

Получить список устройств, затем состояние и декларацию выбранного. По декларации построить элементы управления. Свойство `r` отображать без поля записи; `rw` и настройки показывать с подходящим контролом; `w` показывать как действие.

Значения обновлять примерно раз в секунду через наш API. Не запускать новый запрос, пока прошлый ещё идёт; останавливать опрос при уходе со страницы. При ошибке сохранять последнее значение, но указывать, что оно устарело.

**Готово, когда:** изменение лампы на сервере видно в интерфейсе без перезагрузки. Серийные номера остаются строками и не округляются.

### F3 Сделать команды и режим симуляции

Подключить «Включить лампу» к API команд. После запроса перечитать состояние. Ошибка должна показываться рядом с действием, а кнопка во время запроса — быть недоступной для повторного нажатия.

Кнопку «Имитировать протечку» подключить к отдельному API симуляции с `input=wet`. Не пытаться записать `leak` через API обычных команд. Для термостата предусмотреть тестовый ввод температуры. Добавить «Сбросить демонстрацию» с пояснением, какие состояния сбросятся.

**Готово, когда:** видно изменение эмулятора, а не только текстовое сообщение об успехе.

### F4 Сделать конструктор устройств

Реализовать поля из D4. Первым шагом дать выбор готового шаблона, вторым — редактирование разрешённых полей и сигналов универсального шаблона. Проверять пустые поля, уникальные имена и диапазоны до отправки, а серверные ошибки показывать по нужной строке.

После сохранения перейти к карточке нового устройства. Затем обновить варианты устройств и сигналов в редакторе сценариев. Это важная проверка: новое устройство должно реально стать доступным для автоматизации.

### F5 Сделать редактор сценариев

При выборе устройства подгружать его сигналы. Для условий разрешать читаемые значения. Для действий предлагать только `rw/w`. При смене устройства очищать выбранный сигнал; при смене сигнала очищать несовместимое значение.

Сначала реализовать одно условие и одно действие. Когда первый путь работает, добавить до трёх действий. Добавить сохранение, редактирование, переключатель активности и удаление. Удаление попросить подтвердить внутри приложения, чтобы пользователь не потерял правило случайно.

**Готово, когда:** можно создать два разных правила, перезагрузить страницу и открыть сохранённые данные без потерь.

### F6 Сделать журнал

Отобразить время, причину срабатывания, фактические действия и результат. Для неуспешного действия вывести объяснение из API. Добавить фильтр по сценарию или устройству, если это помещается в срок. Не рисовать историю событий на стороне браузера вместо чтения серверного журнала.

### F7 Сделать статусы Ujin

Взять статус у нашего сервера. Отдельно показать локальное состояние, результат сетевого запроса и подтверждение чтением. Не выводить токены, пароли, полный URL запроса с секретными параметрами.

Если облако недоступно, редактор и локальные сценарии должны оставаться доступны. При восстановлении сети статус обновляется без перезагрузки всей страницы.

### F8 Объединить и проверить

К шестому часу предложенного расписания добиться первого сквозного пути через реальные API. Проверить пустые списки, недоступный сервер, повторное сохранение, длинные названия и узкую ширину. Собрать production-версию интерфейса и передать команду запуска в README.

**Фронтендер закончил работу, когда:** пользователь создаёт устройство и правило, запускает симуляцию, видит реальный результат и ошибки, а данные переживают обновление страницы.


## 5 Архитектура и границы ответственности

Используем Python на сервере, чтобы импортировать готовые эмуляторы без переноса на другой язык. Фронтендер выбирает знакомый ему веб-стек. Для HTTP-сервера предлагаем FastAPI; если команда уже начала на другом знакомом фреймворке, перенос не нужен. Устройство сервера и термины объяснены в отдельном руководстве «Бэкенд простыми словами». Хранилище первой версии — SQLite.

```text
Браузер
  список устройств / конструктор / редактор / журнал
        |
        | наш HTTP API, JSON
        v
Один Python-сервер
  Бэкендер 2: API, сценарии, проверки, SQLite, журнал
        |
        | согласованный интерфейс функций
        v
  Бэкендер 1: экземпляры эмуляторов, шаги времени, команды
        |
        | отдельная очередь публикаций
        v
  Адаптер Ujin --> тестовый стенд --> подтверждение чтением
```

Исполнение сценариев принадлежит нашему серверу. Облачные autoscripts можно добавить позднее после проверки стенда. Это позволяет реализовать требование исполнения уже сейчас. У организаторов нужно уточнить, достаточно ли такого размещения движка для зачёта интеграции; если они требуют именно облачный движок, это отдельная обязательная работа.

### Кто владеет какой частью

| Участник | Основная ответственность | Что передаёт другим |
| --- | --- | --- |
| Продакт | Объём, требования, ответы организаторов, приёмка, защита | Сценарии, таблицу готовности, текст презентации и видео |
| Дизайнер | Пользовательский путь, экраны, компоненты, тексты состояний | Макеты с состояниями и пояснением поведения |
| Фронтендер | Работающее приложение в браузере | Все экраны, формы, обработку ошибок, сборку интерфейса |
| Бэкендер 1 | Устройства, симуляция, интеграция Ujin | Интерфейс среды устройств, реальные состояния и статусы обмена |
| Бэкендер 2 | Наш API, конструктор данных, движок сценариев, хранение | Контракт API, работающие правила и журнал |

**Правило разделения:** бэкендер 1 не пишет второй редактор сценариев, бэкендер 2 не создаёт второй независимый клиент Ujin. Фронтендер работает с нашим сервером, а не с токенами Ujin.

### Соглашение между бэкендерами

Бэкендер 1 предоставляет модуль со следующими операциями. Названия — предлагаемый контракт нового приложения, сейчас этих функций в пакете нет.

| Операция | Что принимает | Что возвращает |
| --- | --- | --- |
| `list_devices()` | Без параметров | Идентификаторы, названия, семейства, статусы |
| `get_declaration(device_id)` | Наш строковый id | Список описаний сигналов |
| `get_state(device_id)` | Наш id | Значения, время обновления, состояние связи |
| `create_device(definition)` | Проверенная декларация | Новый id и состояние экземпляра |
| `apply_command(device_id, signal, value)` | Команду для `rw/w` | Успех или конкретную ошибку и обновлённое состояние |
| `simulate(device_id, input, value)` | Разрешённое воздействие, например `wet` | Результат симуляции и изменённые свойства |
| `step_all(dt)` | Шаг времени | Изменения сигналов для движка и публикации |
| `reset_demo()` | Без параметров | Возвращение демо-устройств в согласованное состояние |

Бэкендер 2 вызывает эти функции из одного процесса. Мутации состояния выполняются последовательно под общей блокировкой или через одну очередь, чтобы тик и HTTP-команда не меняли устройство одновременно. Сеть Ujin работает отдельно и не удерживает эту блокировку.

Предлагаемые места для нового кода внутри выбранного репозитория: `backend/app.py`, `backend/runtime.py`, `backend/ujin_adapter.py`, `backend/scenario_engine.py`, `backend/storage.py`, `backend/schemas.py`, `frontend/`, `tests/`, `docs/`. Это будущая структура, а не список уже существующих файлов. Один участник создаёт каркас; остальные не переименовывают его параллельно.


## 12 Контракт приложения для совместной разработки

Это предлагаемый **новый API команды**, а не существующие методы Ujin. Утвердить в первый час. Изменения согласовывать с фронтендером до реализации.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/health` | Готовность нашего сервера |
| `GET /api/templates` | Шаблоны устройств и доступные способы симуляции |
| `GET /api/devices` | Список экземпляров |
| `POST /api/devices` | Проверить декларацию, сохранить и создать экземпляр |
| `GET /api/devices/{id}` | Название, декларация, состояние и облачное соответствие |
| `POST /api/devices/{id}/commands` | Команда в управляемый сигнал |
| `POST /api/devices/{id}/simulate` | Тестовое воздействие на эмулятор |
| `GET /api/scenarios` | Список правил |
| `POST /api/scenarios` | Создать правило |
| `PUT /api/scenarios/{id}` | Изменить правило |
| `PATCH /api/scenarios/{id}` | Переключить enabled |
| `DELETE /api/scenarios/{id}` | Удалить правило |
| `GET /api/executions?limit=100` | Последние исполнения |
| `GET /api/integration/status` | Статус обмена с Ujin без секретов |
| `POST /api/demo/reset` | Согласованный сброс симуляции |

Пример нашего сценария:

```json
{
  "id": "scenario_1",
  "title": "Световое оповещение о протечке",
  "enabled": true,
  "condition": {
    "device_id": "leak_1",
    "signal": "leak",
    "operator": "==",
    "value": 1
  },
  "actions": [
    {"device_id": "light_1", "signal": "lamp", "value": 1}
  ]
}
```

Пример ответа устройства, сокращённый до одного сигнала:

```json
{
  "id": "light_1",
  "title": "Лампа в коридоре",
  "family": "light",
  "platform_serial": "17036997610001989",
  "platform_ext": "ultraxd_light_01",
  "signals": [
    {
      "name": "lamp",
      "title": "Свет",
      "value_type": "integer",
      "control": "switch",
      "management": "rw",
      "group": "capability",
      "allowed_values": [0, 1],
      "value": 0
    }
  ],
  "integration": {"status": "pending", "verified_at": null}
}
```

Для MVP в штатных семействах переключатели храним как `0/1`, а не смесь `true`, `1` и строки `"1"`. На границе запроса сервер проверяет и приводит данные к согласованному типу. В симуляции `wet` допускает boolean, который runtime преобразует в состояние датчика.

Тело команды лампе: `{"signal":"lamp","value":1}`. Тело воздействия на датчик: `{"input":"wet","value":true}`. Успешная команда возвращает `{"ok":true,"state":{"lamp":1}}`. Для ошибки использовать соответствующий HTTP-статус, например 422 для неверного значения, и тело:

```json
{
  "error": {
    "code": "SIGNAL_READ_ONLY",
    "message": "Этот сигнал доступен только для чтения",
    "field": "signal"
  }
}
```

Перед началом реализации бэкендер 2 дополняет эти примеры точной схемой конструктора и журнала. Фронтендер и бэкендер 1 проверяют, что могут работать по ней. Это задача B2.1, а не повод остановить весь проект до написания документации на десятки страниц.
