# Фронтенд по шагам

> Предыдущая версия плана. Актуальный объём и поведение продукта: [Текущий продукт и состав MVP](../PRODUCT.md). При расхождении используйте актуальную спецификацию. Этот файл не подтверждает готовность приложения.

Сначала прочитай [общий API и поведение](00-common.md). Сейчас в проекте только стартовая страница React. Все функции ниже нужно сделать.

## 1. Запусти нужную папку

Из корня репозитория:

```bash
cd client/hackaton
node --version
npm ci
npm run dev -- --host 127.0.0.1
```

Используй Node 22.12+ или 24. Открой адрес из терминала. Если `vite: command not found`, зависимости не установлены. Если нет скрипта `dev`, ты в `client`, а нужно в `client/hackaton`.

Не создавай второй проект. Внешний `client/package.json` содержит Mantine, но само приложение его не объявляет. Если выбрали Mantine, добавь зависимости именно в `client/hackaton`; для первого соединения достаточно обычных элементов React.

## 2. Подключи наш сервер

В `vite.config.js` сохрани `plugins` и добавь:

```js
server: {
  proxy: { '/api': 'http://127.0.0.1:8000' }
}
```

Перезапусти Vite. Это [прокси запросов](https://vite.dev/config/server-options.html#server-proxy): браузер вызывает `/api/devices`, а Vite передаёт запрос бэку. Для демо на одном компьютере открывай фронт через `127.0.0.1`, не переключай hostname во время сессии.

Создай `src/api.js`: общий `fetch` с JSON, `credentials:'include'`, проверкой HTTP-кода и разбором `{data}` / `{error}`. Показывай `error.message`; при 401 возвращай на вход. Токенов Ujin в браузере быть не должно.

Пока бэк не готов, используй отдельный mock-модуль с теми же полями и подписью «Демо-данные». После подключения сервер становится единственным источником состояний.

**Проверка:** запрос `/api/health` из браузера получает `data.ok=true`. Если приходит HTML вместо JSON, проверь proxy и адрес запроса. `ECONNREFUSED` означает, что бэк не запущен или указан другой порт.

## 3. Покажи устройство и отправь команду

Сделай «Мой дом» по `GET /api/devices` и карточку выбранного устройства по `GET /api/devices/{id}`. Значения читай из `state`, подписи и контролы — из `signals`.

- `r` показывай как показание; обычную запись в него не предлагай.
- `rw` показывай как значение с управлением, `w` — как команду.
- Числа проверяй по диапазону; перечисления показывай по `options`.
- `null` или отсутствующее значение показывай как «Нет данных», не как 0.

Команду отправляй в `/commands`, тестовое показание — в `/simulate`. После команды перечитывай устройство. Не меняй состояние на «Включён» только потому, что пользователь нажал кнопку.

Обновляй данные раз в секунду следующим запросом после завершения предыдущего. При уходе со страницы прекращай опрос. При ошибке сохраняй последнее значение, показывай время и отметку о недоступности. Все id оставляй строками.

**Проверка:** команда меняет состояние на сервере; оно сохраняется после обновления страницы. Симуляция температуры видна в следующем ответе API.

## 4. Собери правило и проверку

Сделай список автоматизаций и форму: название → устройство и показание → сравнение и значение → устройство и команда. Источник вариантов — описание устройств, не заранее зашитые названия.

При смене устройства очищай несовместимый сигнал и значение. Сохраняй через `POST /api/scenarios`, открывай и меняй через GET/PATCH, удаляй через DELETE после подтверждения. Включение — PATCH с `enabled:true`, ответ сервера определяет состояние переключателя.

Кнопка проверки отправляет правило и тестовые входы в `/api/scenarios/test`. Покажи `steps` и `state_after`: данные получены, условие проверено, команда отправлена, результат подтверждён. Не вычисляй успех только в JavaScript.

Историю бери из `/api/executions?scenario_id=...`. `condition_false` — нормальный результат, `waiting_data` — ещё нет результата, `failed` — ошибка. Результат теста показывай отдельно от рабочего журнала.

**Проверка с бэком:** 22 → 18 включает нагреватель, повторное 18 не создаёт второе срабатывание; после выключения правила новые показания ничего не включают. Отдельный тест не меняет состояние дома.

## 5. Добавь вход и доступ по роли

Форма отправляет `login/password` в `/api/auth/login`. После входа получай роль из `/api/auth/me`; после обновления страницы тоже вызывай этот метод. Выход — `/api/auth/logout`.

Пользователь видит дом, каталог и сценарии. Администратор также видит управление моделями и шаблонами. Скрыть кнопку недостаточно: обработай 403 от сервера. До подключения реального входа не выдавай переключатель роли за авторизацию.

**Проверка:** пользователь не открывает административную форму по прямому адресу; после выхода защищённые данные не отображаются.

## 6. Сделай конструктор и добавление устройств

Администратор задаёт название модели, описание, изображение, показания и управляемые состояния. Для сигнала нужны имя, подпись, тип, единица, допустимые значения и начальное значение эмулятора. Для первого конструктора поддержи число и перечисление, доступ `r/rw`. Изменение `rw` задаёт соответствующее состояние универсального эмулятора.

Сохраняй модель через API. Каталог пользователя читает тот же `/api/models`. Действие «Добавить эмулятор» запрашивает имя экземпляра и создаёт устройство через `/api/devices`. Не используй одно устройство на все карточки одной модели.

Покажи ошибки рядом с полями. При 409 `MODEL_IN_USE` предложи создать копию модели. При удалении устройства предупреди об отключении связанных автоматизаций и обнови их список после ответа.

**Проверка:** администратор добавил модель с `fly_count`, пользователь добавил её в дом и может выбрать этот сигнал в условии без изменения фронтенд-кода.

## 7. Добавь готовые сценарии и подбор

В разделе сценариев раздели «Мои» и «Готовые». В шаблоне показывай пользу, подходящие устройства дома и недостающие роли из ответа бэка. Если вариантов несколько, дай выбрать конкретный экземпляр.

При нехватке нагревателя открой подходящие модели каталога. Сохрани незавершённую настройку, чтобы после добавления пользователь вернулся в тот же сценарий. Назначенные роли подставь в обычную форму создания правила.

Администратору дай простую форму шаблона: название, польза, роли с требуемыми возможностями, условие и действие. В MVP два шаблона из инструкции бэка. Покупка — только реальная ссылка на продавца, если она есть; корзину не делаем.

**Проверка:** с одним датчиком видно, что не хватает нагревателя; после добавления можно закончить настройку без повторного выбора датчика.

## 8. Покажи статусы и собери приложение

Из `/api/integration/status` покажи отдельно: локальное действие подтверждено; Ujin принял запрос, но чтение не подтверждено; значение прочитано из Ujin; ошибка связи. Недоступность облака не блокирует локальный редактор.

Проверь пустой дом, отсутствие правил, ошибку формы, недоступный сервер, повторное нажатие, длинное название и узкий экран. На время сохранения блокируй повторную отправку.

```bash
npm run lint
npm run build
```

Для итоговой локальной сборки попроси бэк отдавать `client/hackaton/dist` после маршрутов API. `npm run preview` сам не получает dev-proxy из `server.proxy`; запуск только статики ещё не означает работающий API.

**Готово:** пользователь проходит весь путь от новой модели и добавления устройств до сохранённого правила и подтверждённого результата. После обновления страницы данные остаются, ошибки сервера видны, Ujin не обозначен работающим без подтверждения.
