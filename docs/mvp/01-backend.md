# Бэкенд по шагам

Сначала прочитай [общий API и поведение](00-common.md). Внешние методы Ujin и наши `/api/...` — разные API.

Если бэкендеров двое: первый делает устройства и Ujin, второй — HTTP-сервер, SQLite, вход и правила. Сервер и набор устройств общие, не по одному на каждого.

## 1. Проверь готовые устройства

Из корня репозитория:

```bash
cd docs/ultraxd/emulators
python3 -m unittest discover -s tests -q
```

В этой же папке выполни:

```bash
python3 - <<'PY'
from devices.leak_sensor import LeakSensor
from devices.light import Light
sensor = LeakSensor(serial="sensor", client=None)
lamp = Light(serial="lamp", client=None)
sensor.set_wet(True)
sensor.step()
if sensor.signals["leak"].value == 1:
    lamp.handle_recv({"recv":[{"command":"management","lamp":1}]})
lamp.step()
print("Протечка:", sensor.signals["leak"].value)
print("Свет:", lamp.signals["lamp"].value)
print("Мощность:", lamp.signals["power_w"].value)
PY
cd ../../..
```

Получишь `1`, `1`, `12.0`. `set_wet` задаёт вход, `step` обновляет устройство, `handle_recv` передаёт команду. Это учебный пример; настоящее правило дальше должно читаться из базы. Сеть не используется.

## 2. Подними один сервер

Для нового сервера возьми Python 3.11 или новее. На этой машине системный `python3` — 3.9.6; если `python3.11` отсутствует, сначала установи Python 3.11 и проверь `python3.11 --version`.

Из корня репозитория:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install fastapi uvicorn pytest httpx
mkdir -p backend
touch backend/__init__.py
```

Создай `backend/app.py`:

```python
from fastapi import FastAPI
app = FastAPI()

@app.get("/api/health")
def health():
    return {"data": {"ok": True}}
```

```bash
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Открой `/api/health` и `/docs` на этом адресе. `/docs` — формы для проверки запросов без фронта ([FastAPI](https://fastapi.tiangolo.com/tutorial/first-steps/)). Используй один процесс без `--reload`: перезапуск сбрасывает устройства в памяти. После установки зафиксируй версии зависимостей в `backend/requirements.txt`.

## 3. Соедини API и устройства

Создай `backend/runtime.py`. При старте сервера один раз создай `DeviceRuntime`, внутри — словарь экземпляров устройств. Обработчики запросов используют этот объект, не создают устройства заново.

Дай ему методы `list_devices`, `get_device`, `apply_command`, `simulate`, `step`. Подключи GET устройств и POST команды/симуляции из общего API. Для библиотеки один раз добавь абсолютный путь `docs/ultraxd/emulators` в `sys.path` внутри адаптера: её импорты написаны как `from core import ...`.

Встроенный цикл сервера раз в секунду вызывает `step(1)` и фиксирует снимок состояния. `observed_at` обновляй только при новом измерении или подтверждении состояния, не при чтении снимка. Повторное измерение того же значения тоже свежее. Команды и шаги выполняй последовательно. `client=None` оставь: ожидание Ujin не должно останавливать устройства.

Проверяй id, тип, диапазон и `management` до `handle_recv`: библиотека сама может лишь напечатать ошибку. Симуляция отдельная: для готового датчика `leak` вызови `set_wet(bool(value))`, затем шаг; обычной командой читать/писать `leak` нельзя.

**Проверка:** два GET видят одну лампу; команда изменила серверное состояние, повторный GET это подтвердил.

## 4. Сделай модели и хранение

Добавь `storage.py` с SQLite. Храни модели, экземпляры, последние значения с временем, сценарии и журнал. SQLite уже есть в Python. Все обращения к базе — с параметрами, изменения — в транзакции.

Создай универсальный эмулятор на `Device`/`Signal`: поля берутся из сохранённой модели; `tick` ничего не придумывает; симуляция меняет `r`, команда меняет `rw`. Тип и ограничения храни в модели: исходный `Signal` не содержит полноценного типа данных.

Добавь две модели: датчик `temperature` и нагреватель с состоянием `power=0/1`. Это отдельные простые эмуляторы, не переименованный готовый термостат с собственной физикой. Сделай POST/PATCH моделей и POST устройств. Одно описание должно кормить эмулятор, каталог и редактор правил.

**Проверка:** новая модель «Сканер мух» с `fly_count` создаётся через API, её экземпляр принимает число, сигнал появляется в описании устройства. Перезапуск не теряет модели и правила.

## 5. Запусти сохранённое правило

В `scenario_engine.py` после нового показания находи активные правила с этим входом. Проверь свежесть, оператор и значение; при переходе в истину вызови `runtime.apply_command`. Запиши вход, условие, действие и результат в журнал.

Проверяй правило при сохранении: устройства существуют, условие читает `r/rw`, действие использует `rw/w`, типы совпадают. Не используй `eval`. Одно событие обрабатывай один раз; добавь ограничение длины цепочки, чтобы два правила не включали друг друга бесконечно.

POST теста создаёт отдельные копии только участвующих эмуляторов, применяет тестовые входы и выполняет одно переданное правило. Возвращает шаги и состояния. Не изменяет основной runtime, активность и очередь Ujin.

**Проверка:** 22 → 18 включает нагреватель один раз; следующее 18 не повторяет команду; после 22 → 18 команда снова выполняется. Выключенное правило, отсутствующее или старое показание команду не запускают. Тест не меняет живой дом.

## 6. Добавь вход и готовые сценарии

Сделай две локальные учётки: `admin` и `user`. Пароли задаются конфигурацией, в базе хранятся хеши. После входа выдавай случайную серверную сессию в HttpOnly cookie с SameSite=Lax; роль проверяй на сервере. Чужая роль из запроса ничего не разрешает. Это учётки нашего приложения, не аккаунты Ujin.

Создай два шаблона: «Согреть комнату» и «Выключить нагрев при высокой температуре». В шаблоне храни роли устройств с нужными `capability`, условие и действие. Подбирай устройства по возможностям, не по русскому названию. Ответ шаблона содержит подходящие `device_ids`, недостающие роли и подходящие `model_ids`. Назначение устройств превращает шаблон в обычное правило.

**Проверка:** пользователь не может создать модель через прямой запрос; при отсутствии нагревателя шаблон предлагает его модель. После добавления устройства то же правило можно настроить.

## 7. Подключи Ujin отдельно

Прочитай [PULL-CLIENT](../ultraxd/PULL-CLIENT.md) и [клиент](../ultraxd/emulators/ujin_client.py). Доступы загружай на сервере из `docs/ultraxd/доступы.json`, не копируй в код и фронт.

1. Получи токен сотрудника: POST form `https://api-uae-test.ujin.tech/api/auth/authenticate/`, поля `login`, `password`, `app=employee`; токен в `data.user.token`.
2. Прочитай тестовое устройство: GET `bmsdevice/get-device-info` с `token`, `serialnumber=17048805610017116`, `mts=1`. Карточка уже подтверждалась. Не создавай её повторно.
3. Для публикации возьми `residents[0].ust`. Query: `token`, `apartment_id=2860`, `serialnumber=ultraxdfly20261031`. POST JSON в `import_device/group-update-device-signal/`:

```json
{"data":[{"sn":"ultraxdfly20261031","s":"fly_count","v":12,"c":"integrations_devices"}]}
```

4. Через 3 секунды отправь ту же строку с `s=integrations_devices_fly_count`. Затем прочитай значение независимо. Повтори с 28. `error=0` без обратного чтения не подтверждает обмен.
5. Передавай в браузер отдельные статусы: `not_configured`, `pending`, `accepted_unverified`, `verified`, `error`. Копии изменений складывай в очередь вне `Device.flush`: он очищает изменения даже при неудачной отправке. Ставь timeout, ограниченные повторы и время последней попытки.

В проверке 31 октября 2026 обе публикации вернули HTTP 200, `error=0`, `result:[null]`; значения 12 и 28 при обратном чтении не появились. Полные ответы сохранены локально у продакта. После одной проверки правильного формата фиксируй блокер и продолжай локальный MVP. Не перебирай ручки. У интеграционного cos-токена есть ограничение по IP; смена машины или VPN может влиять на доступ. К публикации через UST это объяснение автоматически не относится.

**Ограничения:** `sn` в JSON — внешний id, числовой serial используется при чтении. `c` — класс `integrations_devices`. Новый сигнал требует двух фаз. Замена 0 на 0.001 есть в исходном клиенте; применяй её только на границе Ujin для проверенного сигнала, никогда в локальном состоянии. Словарь `r` не принимает команды вниз; `rw` настраивают организаторы. Не строй MVP на WebSocket или платформенных autoscripts: их работа на нашем стенде не подтверждена. `ports/`, `quality/`, панель организаторов и их БД в пакете отсутствуют.

## 8. Передай результат фронту

Передай рабочие адреса `/docs`, две демо-учётки отдельно от кода и примеры ответов общего API. Проверь сохранение после перезапуска, роли, диапазоны, отсутствие данных, повторное событие и изоляцию теста. Финальная проверка — пользователь создаёт новое устройство и правило в браузере, а сервер выполняет его и возвращает журнал.
